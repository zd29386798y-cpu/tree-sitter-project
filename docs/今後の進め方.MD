# フェーズ3：タスク相関図生成

## 目的

`message_edges` をもとに、タスク間の起動・連携関係を可視化する。

## 追加CLI

```powershell
python main.py --mode task-graph
```

イベント指定版：

```powershell
python main.py --mode task-graph --event EVT_START
```

## 入力

* message_edges
* files
* middleware_calls

## 出力

```text
output/task_graph.dot
output/task_graph.xlsx
output/task_graph_<event_id>.dot
output/task_graph_<event_id>.xlsx
```

## 追加テーブル

```sql
task_edges
```

列：

```text
id
event_id
from_task
to_task
message_id
data_name
caller_function
file_id
line
confidence
edge_reason
```

## 処理方針

1. `message_edges` から `from_task`, `to_task` を取得
2. `UNKNOWN` は残す
3. `from_task -> to_task` のエッジを作る
4. event_id ごとに分類
5. DOT形式で出力
6. Excelでも一覧出力

## 注意

最初は完全なチェーン追跡をしない。
まずは「タスクA → タスクB」の直接相関図だけ作る。

# フェーズ4：イベント別タスクチェーン解析

## 目的

イベントIDを起点に、複数タスクにまたがる処理チェーンを追跡する。

## 追加CLI

```powershell
python main.py --mode event-chain --event EVT_START
```

## 出力

```text
output/event_chain_EVT_START.xlsx
output/event_chain_EVT_START.dot
```

## 追加テーブル

```sql
event_chains
```

列：

```text
id
event_id
depth
route_order
from_task
to_task
message_id
data_name
caller_function
file_path
line
confidence
visited_key
```

## 処理方針

1. 指定event_idの `message_edges` を取得
2. `from_task -> to_task` のグラフを作る
3. 開始ノード候補を推定
4. DFS/BFSで後続タスクをたどる
5. ループ検出を入れる
6. depthを付与する

## ループ対策

同じ組み合わせは再訪問しない。

```text
event_id + from_task + to_task + message_id + data_name
```

を visited_key とする。

## 出力イメージ

```text
EVT_START
  depth 0: TASK_A -> TASK_B
  depth 1: TASK_B -> TASK_C
  depth 2: TASK_C -> TASK_D
```

# フェーズ5：データフロー解析

## 目的

タスク間でどのデータが読み書きされ、どこへ渡されるかを解析する。

対象：

* MESSAGE
* FILE
* DB
* SHARED_MEMORY
* TABLE
* BUFFER

## 追加CLI

```powershell
python main.py --mode data-flow
```

イベント指定：

```powershell
python main.py --mode data-flow --event EVT_START
```

データ指定：

```powershell
python main.py --mode data-flow --data DATA_NAME
```

## 入力

* data_accesses
* message_edges
* middleware_calls
* functions
* calls

## 出力

```text
output/data_flow.xlsx
output/data_flow.dot
output/data_flow_EVT_START.xlsx
output/data_flow_EVT_START.dot
```

## 追加テーブル

```sql
data_flow_edges
```

列：

```text
id
event_id
from_task
to_task
from_function
to_function
data_name
data_kind
direction
access_type
source_type
file_id
line
confidence
reason
```

## 処理方針

### 1. MESSAGE由来

`message_edges.data_name` を使って、

```text
from_task SEND data_name
to_task RECEIVE data_name
```

を作る。

### 2. FILE由来

`data_accesses` の file_read / file_write から、

```text
TASK_A WRITE FILE_X
TASK_B READ FILE_X
```

を同じ `data_name` でつなぐ。

### 3. DB/共有メモリ由来

同じく、

```text
TASK_A WRITE TABLE_X
TASK_B READ TABLE_X
```

をつなぐ。

## 注意

最初は変数代入の追跡まではしない。
ミドルウェア関数の引数に出てきたデータ名だけを使う。

* BFSまたはDFSで後続タスクを探索

# 設計上の重要方針

1. 推定結果には必ず `confidence` を持たせる
2. 根拠ファイル、行番号、関数名を保持する
3. UNKNOWNを消さない
4. 最初から100%正確を狙わない
5. 現場ルールで育てる前提にする
6. Excelで人間が確認できる形を優先する
7. DOT/HTMLはレビュー用とする
8. マクロ展開、関数ポインタ、#ifdef完全評価は後続課題とする

最初にCodexへ頼むなら、上の中の **「フェーズ3 task-graph」だけ** を渡すのが良いです。
いきなり全部渡すと設計がブレるので、`task-graph` → `event-chain` → `data-flow` → `business-route` の順で進めるのが安全です。
