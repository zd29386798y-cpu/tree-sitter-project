現状の前提

以下は実装済みです。

分類実装済み項目
基本解析Cソース再帰走査、tree-sitter AST解析、関数・呼び出し・include・型・マクロ抽出、SQLite保存、Excel出力、DOT出力
ミドルウェア支援suggest-rules、generate-rules-template、inspect-calls、list-rules、middleware、event-route
主要テーブルmiddleware_calls、message_edges、data_accesses

実装順序

  1. task-graph: まずタスク間の直接関係を固める。
  2. event-chain: イベント起点で複数段のタスクチェーンを追う。
  3. data-flow: データのread/writeをタスクや関数に紐付ける。
  4. business-route: タスクチェーンとデータフローを業務ルートとして統合する。
  5. report: HTMLでレビューしやすい資料にする。

フェーズ3: タスク相関図 最優先

追加CLI

python main.py --mode task-graph
python main.py --mode task-graph --event イベントID

追加テーブル

task_edges:
id, event_id, from_task, to_task, message_id, data_name,
caller_function, file_id, line, confidence, edge_reason

出力

output/task_graph.xlsx
output/task_graph.dot
output/task_graph_.xlsx
output/task_graph_.dot

受け入れ条件

  • message_edges が空でもエラー終了しない。
  • UNKNOWN を含む行も欠落しない。
  • event指定時に対象event_idだけ出る。
  • ExcelとDOTが出力される。

フェーズ4: イベント別タスクチェーン

追加CLI

python main.py --mode event-chain --event イベントID

追加テーブル

event_chains:
id, event_id, depth, route_order, from_task, to_task,
message_id, data_name, caller_function, file_path, line,
confidence, visited_key

処理方針

  • task_edges からイベント別グラフを作る。
  • BFSを基本にして depth を付与する。
  • visited_key でループを防止する。

フェーズ5: データフロー解析

追加CLI

python main.py --mode data-flow
python main.py --mode data-flow --event イベントID
python main.py --mode data-flow --data データ名

追加テーブル

data_flow_edges:
id, event_id, from_task, to_task, from_function, to_function,
data_name, data_kind, direction, access_type, source_type,
file_id, line, confidence, reason

関連付け

由来作り方
MESSAGEmessage_edges.data_name から SEND / RECEIVE を作る。
FILEfile_write と file_read を同じ data_name でつなぐ。
DBdb_write と db_read を同じ data_name でつなぐ。
SHAREDshared_write と shared_read を同じ data_name でつなぐ。

フェーズ7: HTMLレポート

追加CLI

python main.py --mode report --event イベントID

内容

  • イベント概要
  • タスク相関図
  • データフロー
  • 業務処理ルート
  • 根拠ソース、confidence、UNKNOWN一覧

推奨モジュール構成

analyzer/task_graph.py
analyzer/event_chain.py
analyzer/data_flow.py
analyzer/business_route.py
analyzer/report_writer.py

main.py にはCLI接続だけを追加し、解析ロジックは個別モジュールへ分離します。

最初の実装依頼

最初はフェーズ3だけを依頼します。

フェーズ3として task-graph モードを追加してください。

要件:
- python main.py --mode task-graph
- python main.py --mode task-graph --event イベントID
- message_edges から from_task -> to_task の task_edges を作成
- UNKNOWN は除外しない
- SQLiteに task_edges テーブルを作成
- output/task_graph.xlsx と output/task_graph.dot を出力
- event指定時は output/task_graph_.xlsx と output/task_graph_.dot を出力
- message_edges が空でもエラー終了しない
- py -3.13 -m py_compile で構文確認する

リスクと対策

リスク対策
arg_indexが誤っているinspect-calls で実例確認し、少数ルールから始める。
UNKNOWNが多い除外せず、ルール改善対象として出力に残す。
タスク名の粒度が合わない後続でタスク名正規化ルールを追加する。
DOTが大きくなりすぎるevent指定、data指定、depth制限を追加する。

完了判定

  • イベントIDを指定して、タスク間の起動関係が確認できる。
  • イベントに関係するデータのread/write候補が確認できる。
  • 業務処理ルートとして、イベント、タスク、メッセージ、データアクセスが1つの表で確認できる。
  • すべての出力に根拠ファイル、行番号、confidenceが残る。
  • UNKNOWNや低confidenceがレビュー対象として見える。
