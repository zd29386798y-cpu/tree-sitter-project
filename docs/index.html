概要

このツールは、C言語ソースをtree-sitterで解析し、関数一覧、include一覧、関数呼び出し一覧、 構造体・typedef・enum・マクロ一覧をSQLite DBに保存する解析マップ生成ツールです。

フェーズ2では、関数呼び出し一覧をもとにミドルウェア関数を抽出し、タスク間メッセージ連携 とデータアクセス解析の土台を作ります。

このツールの目的

  • 大規模Cソースの構造を、手作業より短時間で把握する。
  • 関数定義、関数呼び出し、include、型、マクロを一覧化する。
  • SQLite DBとして保存し、再検索や後続解析に使える形にする。
  • Excelで現場メンバーが確認しやすい資料を出す。
  • ミドルウェア関数呼び出しから、イベント、タスク、データアクセスの関係を育てる。

コマンド機能主な出力・確認ポイント
ast指定ソースのtree-sitter ASTを標準出力に表示する。パーサが動くか、サンプルCが読めるかを最初に確認する。
scan指定フォルダ配下の .c / .h を再帰検索する。解析対象ファイル数と除外フォルダの効き方を確認する。
analyzeCソースを解析し、関数・呼び出し・include・型・マクロをSQLiteへ保存する。output/c_analysis.db を作成する。以降の処理の土台。
exportSQLite DBの内容をExcelへ出力する。functions.xlsx、calls.xlsx、message_edges.xlsx などを確認する。
graph関数呼び出し関係をDOT形式で出力する。output/call_graph.dot を生成する。
suggest-rulescalls を集計し、ミドルウェア候補関数を抽出する。callee_summary.xlsx と middleware_rule_candidates.xlsx を確認する。
generate-rules-template候補ExcelからルールテンプレートJSONを作成する。middleware_rules.template.json を生成する。初期状態は全候補無効。
list-rules現在有効な middleware_rules.json のルールだけを一覧表示する。active_middleware_rules.xlsx で有効ルールを確認する。
inspect-calls指定関数の呼び出し実例と引数分割結果を表示する。arg0 から arg5 を見て、各 arg_index を決める。
middleware有効ルールに一致した呼び出しを抽出し、連携候補テーブルを作る。middleware_calls、message_edges、data_accesses を作成する。
event-route指定イベントIDのメッセージ連携と関連データアクセスを表示する。event_route_イベントID.xlsx でイベント別の最小ルートを確認する。
clean-projectGitHub公開前や他PC移行前に、現場ソース由来の解析成果物を削除する。output 配下の *.db、*.xlsx、*.dot、*.csv と __pycache__ を削除する。samples と docs は残す。

順番作業役割・確認内容
1analyze実ソース全体を解析し、SQLite DBを作る。ここで得た calls が後続解析の入力になる。
2export基本解析結果をExcel化し、関数数・呼び出し数・型情報などの全体感を確認する。
3suggest-rules実際に出現している呼び出し先名から、ミドルウェア候補を洗い出す。
4generate-rules-template候補をJSONテンプレート化する。すべて無効状態なので、誤抽出を防げる。
5copyテンプレートを実運用ファイル middleware_rules.json としてコピーする。
6notepad現場知識でルールを編集する。まず少数だけ enabled: true にする。
7list-rules有効化したルールだけを一覧化し、意図しないルールが有効になっていないか確認する。
8inspect-calls対象関数の実際の引数並びを見て、event_arg_index や data_arg_index を調整する。
9middleware調整済みルールでミドルウェア呼び出しを抽出する。
10exportmessage_edges.xlsx と data_accesses.xlsx を出力し、抽出結果を確認する。
11event-routeイベントID単位でタスク間連携の見え方を確認し、次のルール改善に戻す。
12clean-projectGitHub公開前や他PC移行前に実行する。現場ソース由来のDB、Excel、DOT、CSVを削除し、公開してよいファイルだけを残す。

現場でのミドルウェアルール調整手順

  1. suggest-rules で候補を出す。
  2. generate-rules-template でテンプレートを作る。
  3. middleware_rules.json を編集する。
  4. まず少数の関数だけ enabled: true にする。
  5. inspect-calls で引数位置を確認する。
  6. event_arg_index / to_task_arg_index / from_task_arg_index / data_arg_index を調整する。
  7. middleware を実行する。
  8. message_edges.xlsx / data_accesses.xlsx を確認する。
  9. 問題なければ対象関数を増やす。
ルールは最初から広く有効化せず、少数の関数で引数位置と抽出結果を確認してから広げるのが安全です。

今後の進め方

  1. 小規模ソースで analyze から export まで確認する。
  2. 実ソース全体を解析し、calls.xlsx と callee_summary.xlsx を確認する。
  3. ミドルウェア候補を少数選び、inspect-calls で引数位置を確定する。
  4. middleware_rules.json に有効ルールを少しずつ増やす。
  5. message_edges.xlsx と data_accesses.xlsx を見て、現場知識で補正する。
  6. イベントID別に event-route を確認し、タスク起動相関の候補を洗い出す。
  7. 次フェーズでタスク相関図、データフロー図、業務処理ルート解析へ拡張する。

注意事項・制限事項

解析結果は100%正解ではありません。現場ルールを育てながら、段階的に信頼度を上げる前提です。
  • tree-sitterはプリプロセッサ展開を行わない。
  • マクロ経由呼び出しは取れない場合がある。
  • 関数ポインタ呼び出しは完全には解決しない。
  • Excelは1セル32767文字制限がある。
  • DBにはExcelより詳細な情報が残る場合がある。
  • 解析結果は100%正解ではなく、現場ルールで育てる前提。
  • まずは小規模ソースで確認してから全体解析する。
